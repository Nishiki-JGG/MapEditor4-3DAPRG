# 固定サンプルの完成データ同梱

811e26dは完成状態を端末にキャッシュしましたが、端末初回の岩仕上げ・衝突準備は残っていました。固定の2サンプルは配布前に処理を済ませ、初回から完成データを復元する方式へ変更しました。単なる距離計算の高速化ではありません。

## 読込と再計算の境界

- 標準の森林サンプル64m / seed7と、遺跡サンプル48m / seed11を同梱。選んだサンプルだけを読み込みます。
- 有効な端末キャッシュ → 同梱された完成品、の順で使います。キャッシュ保存が使えなくても固定サンプルは完成品を読み直し、重い生成には戻りません。
- 新しいランダムseed、別サイズ、編集した体格・カタログなど、完成品と条件の異なる生成は従来の生成器で処理します。地形編集・岩の位置/角度/縮尺変更は既存どおり古い適合・衝突情報を無効化します。
- モデルの構築、GPUへの転送、初回シェーダー準備・描画は端末側に残ります。準備中の表示・中止・TAB予約も維持します。
- 通常の保存JSON形式とUnity書出し形式は変更していません。ユーザーの保存先をキャッシュで上書きしません。

## 同梱内容と容量

完成配置・地形・加工岩geometry、倍率別の元部品距離場、加工岩の距離場/境界、通行マスクと床高を含みます。モデル頂点・衝突値を量子化していません。元geometryからの可逆な整数ビット差分、差分の共有、型付き配列のパック、gzipで縮めています。加工岩で距離場生成後に不要な中間高さ配列は配布せず、編集時にはその加工岩自体を無効化します。

| サンプル | gzip本体 | 配布JS実体 | JSをHTTP gzipした場合の参考値 | パック展開後 |
|---|---:|---:|---:|---:|
| 森林64m | 5,924,829 B | 7,899,834 B | 5,938,545 B | 23,375,001 B |
| 遺跡48m | 2,403,425 B | 3,204,632 B | 2,407,533 B | 9,940,961 B |

表のHTTP圧縮はビルドツールによる参考値で、配信環境の実転送量を保証しません。localhostの無圧縮配信ではJS実体の容量を取得しました。`file://`直接起動も保つためデータはJSラッパー内のbase64です。最初の単純な試作は森林のgzipだけで20.4MBとなり不採用にしました。現在も通信・復号と一時メモリが必要です。端末キャッシュが有効なら再ダウンロード・展開は省きます。

## 整合性と失敗時

生成レシピ版、サイズ・seed・biome・体格・カタログ、スクリプト版と元geometryのfingerprintを照合します。配布ファイル名は内容hash付きです。圧縮サイズ・SHA256・展開サイズ・形式版・各配列長、元部品/加工岩/通行マスクとの対応を検証します。

壊れた端末キャッシュは破棄して同梱版を試します。同梱版が不一致・欠損・破損した場合はエラーを表示し、元のマップへ復帰します。そこで重い生成を黙って開始しません。gzip展開APIのない古いブラウザも明示的に停止します。中止した古い読込が新しいマップへ適用されないよう既存の世代検査を使います。

復元途中のマーカー配置から仮の歩行領域を再計算していた経路も、完成岩・衝突・通行マスク適用後へ順番を変更しました。

## 検証

以下は海の並行更新3148998を統合する前の記録です。ユーザーPCのChrome、1280×720、同じ森林マップ/カメラ、使い捨てprofile・キャッシュなし、loopback配信で811e26d→今回を順番に測定しました。GPUドライバー/OSのキャッシュは消していません。

| 条件 | 準備完了 | 最大long task |
|---|---:|---:|
| 811e26d 森林初回（端末で仕上げ計算） | 13.746秒 | 457ms |
| 今回 森林初回（完成品復元） | 7.779秒 | 642ms |
| 今回 森林をRAMから再利用 | 2.967秒 | 282ms |
| 今回 森林をページ再読込後に再利用 | 3.150秒 | 263ms |
| 今回 遺跡初回・別検査 | 5.375秒 | 329ms |
| 今回 新ランダムseed23 | 10.866秒 | 475ms |

森林初回の別実行は7.655秒/290ms、file直接起動は7.536秒でした。最大停止が常に短くなったとは言えません。比較実行の642msは初回描画の準備段階にあり、初回GPU/描画処理には依然として短い同期停止が残ります。TABを準備中に押して完了後2.5秒歩行した区間は約9.75m移動し、岩の変化・long taskともありませんでした。ここで測ったネットワークは高速なlocalhostであり、実配信の初回通信待ちとは別です。

ユーザーPCの使い捨てChromeで検証します。ユーザーの作業タブや保存ファイルは操作しません。固定2種それぞれでキャッシュなしの同梱復元を確認し、通常生成器の結果と、保存マップ全体・0.5m格子の通行判定・全加工岩の距離場/境界値をhashで照合しました。森林は5,761配置/加工岩552、遺跡は326配置/加工岩226で一致しました。

破損時の元マップ復帰、壊れたキャッシュからの同梱読込、回転/縮尺編集後の衝突無効化と保存読込、IDのない旧保存、地形編集、生成中止・連続生成、大きな保存のページ間引渡しも検証対象です。モデル数・三角形・材質・画像・影描画の仕様は増やしていません。スマホ実機、低速回線、全ブラウザの性能は未測定です。

再現手順（Node.js、Chrome/Edge）:

```powershell
node tests/prepared-codec.test.cjs
node tests/prepared-loader.test.cjs
node tools/build-prepared-samples.cjs --check
$env:SUITE='sample' # sample2も別実行
node tests/prepared-browser.cjs
node tests/prepared-file.cjs
$env:SUITE='flow' # randomも別実行
node tests/preparation-browser.cjs
```

配布用データの再生成は `node tools/build-prepared-samples.cjs` です。生成元を変更したら必ず再生成し、`--check` を通します。これは保守時の処理で、利用者の初回起動では実行しません。

海の並行更新3148998は通常マージで保全し、index.htmlのscript版をsea3とprepared1の両方へ合わせました。固定サンプルもその版で再生成しています。水の処理をこの改善で独自に変更していません。Windowsの既存CRLF差によりsea_hlsl_syncの生比較は失敗し、MapSeaShared.hlslの読込改行のみをLFへ正規化した比較で全項目が一致しました。製品の海ファイルはmainのものを維持しています。

統合後もキャッシュなしの森林7.721秒（最大317ms）、遺跡5.141秒（最大763ms）、岩適合0回・距離場miss0を確認しました。両方の生成器との完全一致、破損時復帰、編集・保存読込が通過しています。763msの起動時停止は未解消として残し、スマホ性能の合格には扱いません。
