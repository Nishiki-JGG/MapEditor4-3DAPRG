## 指摘1：世界の広さと Unity Terrain の解像度を分ける

**修正**
- 書き出しのグリッドを、エディター内部のグリッド（0.5m 間隔、頂点 2×広さ+1）から切り離しました。
- Unity の heightmapResolution の候補（33, 65, 129, 257, 513, 1025, 2049, 4097）のうち、エディターの頂点数以上で最も小さい値を使います。間隔は 広さ ÷ (解像度 − 1) です。部屋の広さは変わりません。

  | 広さ | エディター内部 | 書き出し（高さ） | 間隔 | 穴 |
  |---|---|---|---|---|
  | 24m | 49 | **65** | 0.375m | 64 |
  | 32m | 65 | 65 | 0.5m | 64 |
  | 48m | 97 | **129** | 0.375m | 128 |
  | 64m | 129 | 129 | 0.5m | 128 |
  | 96m | 193 | **257** | 0.375m | 256 |
  | 128m | 257 | 257 | 0.5m | 256 |

- 書き出しの頂点ごとの決め方（meta の `coordinateSystem.grid.sampling` に記載）：
  - 高さ：エディターの高さを双線形で補間
  - 歩く床：エディターの歩く床（橋・階段・隠し通路を含む）の値
  - 地面の重み：塗りの値を双線形で補間してから合成
  - 塗りの元データ（mask）：いちばん近いエディター頂点の値をそのまま使う（ぼかさない）
  - 通行判定：書き出しの頂点ごとに同じ `walkable()` で判定し直す（補間しない）
  - 穴：隠し通路の形から作る（指摘2）
- meta：`grid.count / spacing / unityTerrainCompatible / editorGrid`、`terrain.heightmapResolution / cellSize / holesResolution`、RAW の説明の間隔、README を更新しました。map.json だけは従来どおりエディター内部のグリッドです。
- Importer 側での変換は不要です。ZIP の RAW と PNG をそのまま TerrainData に設定できる解像度で出しています。

**確認結果**（全 6 サイズ）

| 広さ | 解像度 | 対応値か | RAW のバイト数 | PNG（穴） | 四隅の高さの差 | 開始地点の位置（meta / エディター） | 開始地点の高さの差 | 書き出しグリッドでの到達 |

- 24・32・96・128m は、平らな部屋に尾根と隠し通路を置いた試験用の部屋で調べました。
- 書き出しグリッドでの到達：書き出した walkable.png だけを使い、開始地点から 8 方向（斜めの角抜けなし）に探索しました。サンプル2では、尾根の向こう（通路の先）にある宝箱と下り階段にも届いています。通路を通れる形のまま変換できていることの確認です。

- 通常サンプル（64m）は解像度が変わらないので、heightmap・walk_floor・walkable・weights のファイルは r5 とバイト単位で同じでした。

## 指摘2：隠し通路の形と地形の穴を同じ境界から作る

**決まり**（meta の `secretPassages.shapeRule`）
- **正本**：通路の頂点（O=3）を中心とする 0.5m 四方の和集合です。これはエディターの通行判定（`overrideAt` の最近傍）が実際に歩く範囲そのものです。厳密な輪郭を `passages[].outline`（Unity 座標）に出力します。
- **穴（holes.png）**：正本のうち、床の上に 0.3m より厚い岩がある部分に重なる、書き出しのセルすべて。
- **通路メッシュ（`secret_passages_mesh.json`）**：同じ正本から 0.125m の格子で作ります。0.125m は四方の辺（0.25m ずれ）と書き出しのセル（0.375m / 0.5m）の両方を割り切るので、どちらも近似せずに扱えます。
  - floor：正本の上の床（エディターの床の高さ）
  - wall：輪郭に沿った壁。入口（外側が歩ける地面で、段差が上限以内）には作りません。
  - ceiling：床の上の岩が `clearanceHeight`（身長 + 0.6m = 2.4m）より厚い所に、床 + 2.4m の天井
  - 入口の上と、天井のある所・ない所の境目に、天井から地表までをふさぐ面
  - cap：穴のセルのうち、天井のない切り通しでない所すべてに、書き出した高さに合わせた地表面
- Unity 座標・時計回りの面で出力しています。MeshCollider としてそのまま置けます。
- `route` と `width` は**目安**です（`routeIsGuideOnly`、`widthIsAverage`）。meta の note も「route から形を作らない」と直しました。

**確認結果**（サンプル2、48m → 129×129。数値は試験コードが出力ファイルから独立に計算したもの）

| 項目 | 値 |
|---|---|
| 通路の面積（正本） | 22.0m² |
| そのうち岩の下 | 14.5m² |
| 岩の下で、穴の中に入っている部分 | **14.5m²（100%）**＝通路に地形は残らない |
| 穴のセル | 128（18.0m²）。全セルが通路の岩の下の部分に接している |
| 穴の面積のうち、メッシュ（床・ふた）で覆われない部分 | **0m²** |
| 穴のうち、通路の外にはみ出しふたで覆った部分 | 15.6m²（天井の上のふたを含む） |
| 体が通れる最も狭い幅（入口から出口まで） | 1.375m（必要 0.6m） |
| 入口・出口 | 2 か所とも床が外の地面につながる |
| 輪郭 | 1 本（Unity x 15.75〜19.25、z 12.25〜22.75） |

- 他のサイズ（24 / 32 / 96 / 128m の試験部屋）でも、岩の下の通路は 100% 穴の中、覆われない穴は 0m²、最も狭い幅は 2.375m でした。
- 前回 Astra が挙げたずれ（例：z=17〜17.5 の穴が x=17〜19.5 で、平均幅で押し出した通路と合わない）は、穴とメッシュを同じ正本から作るようにしたので起きません。
- エディターの検証にも追加しました。覆われない穴・通路に残る地形はエラー、最も狭い幅が体の幅より狭ければ警告です。
- 未確認：Unity のふたと Terrain の境目。Terrain はセルを三角形 2 枚に分けるので、双線形で作ったふたとの間に、そのセルの補間誤差ぶんの段差が出る可能性があります。
