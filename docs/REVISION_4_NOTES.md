## 残件1：橋・階段の幅不足が地面判定へ戻る【P1】

**修正**
- 構造物があるかどうかの判定と、体が収まるかどうかの判定を分けました。
  - 構造物の範囲：`bridgeAt` / `stairsAt` の既定余白を 0 にし、床そのものの範囲で判定します。
  - 体が収まる範囲：余白を agentProfile.radius にして判定します。
- 構造物の範囲内では、その床を使います。次のどちらかなら**通れない**とし、下の地面の判定には戻しません。
  - 体が収まる範囲から外れている。
  - 床の上に障害物がある。
- `floorAt` も同じ `deckAt(x, z, 0)` で床を選びます。通行判定・床の高さ・walk_floor の RAW・walkable.png の判定が一致します。
- 複数の床が重なる場所（下の床を使うこと）は、今回も対象外です。

**確認結果**（地面は乾いた歩ける谷底で高さ 0。橋は幅 2.4m、床の高さ 3.12m）

| 条件 | 結果 | 床の高さ |
|---|---|---|
| 半径 0.3、橋の中央 | 通れる | 3.12 |
| 半径 1.3、橋の中央 | **通れない** | 3.12 |
| 半径 0.3、中央から横へ 1.0m | **通れない** | 3.12 |
| 半径 0.3、中央から横へ 0.8m | 通れる | 3.12 |
| 橋の外（横へ 2m）の地面 | 通れる | 0 |
| 橋の上に通行禁止を指定 | 通れない | — |
| 橋の床の上に障害物 | 通れない | — |
| 階段（幅 1.2m）、半径 0.3、中央 | 通れる | 4 |
| 階段、半径 0.3、横へ 0.45m | **通れない** | 4 |
| 階段、半径 0.7、中央 | **通れない** | 4 |

橋がなければ、この谷底は通れる場所です。修正前は、上の表で**太字**にした「通れない」がいずれも「通れる」と判定されていました。

## 残件2：yawOffsetDeg と衝突形状の座標の決まりがずれる【P1】

**決まり（カタログの `frame` に明記）**
- カタログの形状（offsets・solid・trigger・arrival）は、**実際の Prefab のローカル座標**で書きます。
- Unity では `yawDeg + yawOffsetDeg` で回して置きます。
- エディターの衝突判定にも同じ yawOffsetDeg を使います。換算は `論理座標 = rotY(yawOffsetDeg) × Prefab座標`、`エディター座標 = 論理座標の (x, −z)` です。
- 入口・到着点はゲーム上の意味で決まる位置なので、yawOffsetDeg を変えても世界座標では動きません。カタログには、それを Prefab 座標へ戻した値を出力します。
- 小物の offsets（Prefab の X 方向）も yawOffsetDeg と一緒に回ります。内部では 2 次元の点として持ちます。
- 読み込んだカタログの値をそのまま保持し、そのまま再出力します（往復で丸めのずれが出ません）。

**確認結果**
- 条件：yawOffsetDeg を 0 / 90 / −90、yaw を 0 / 90 / 180 / 270 にした全組み合わせ。
- 使った資産：
  - 左右非対称な小物（倒木、offsets = [0, 1.5]）
  - 非対称な衝突円を持つ上り階段（solid = [[0, 0, .5], [1.5, 2.0, .3]]）
- 一致を確かめたもの：
  - 内部の衝突判定を Unity 座標に直したもの
  - 出力の colliders・trigger・arrival
  - 決まりどおり Prefab を回して求めた形状

  結果：すべて一致（誤差 0m）。
- trigger・arrival の世界座標は、yawOffsetDeg が 0 のときと比べて 0m のずれ。
- カタログの solid・offsets は往復しても同じ値。

## 残件3：Float32 の高さ配列の異常と長さ不足を受け付けてしまう【P2】

**修正**
- 地形を書き換える前に、すべてを一時配列に読み込んで検査するようにしました。検査に通ったときだけ、まとめて地形に反映します。
- 検査する内容：
  - 高さ（heightsF32 / 旧形式 heightsCm）：バイト長、NaN・Infinity・±1000m 超の値
  - splat：長さが N×N の 1〜9 倍か
  - walkOverride：長さと、値が 0〜3 の範囲か
  - その他：base64 として読めるか、props などが配列か
- 読み込みボタンでは、成功したときだけ取り消し履歴に記録します。

**確認結果**
- 次の 10 種類の壊れた入力をすべて拒否しました。拒否した前後で、地形・roomId・ID・配置・通行の上書きは同じままです。
  1. 高さに NaN
  2. 高さに Infinity
  3. 高さが 1 要素だけ
  4. 高さの要素が 1 つ多い
  5. 4 で割り切れないバイト長
  6. 旧形式（heightsCm）で長さが足りない
  7. splat の長さが不正
  8. walkOverride に 7
  9. base64 として読めない
  10. props がない
- 正しい新形式は往復で完全に一致しました。
- 旧形式（cm）も読めます。高さの差は最大 0.005m（cm に丸めた分）で、ID はすべて保持しました。

## 追加：サンプル2（遺跡・隠し通路）

ユーザーの依頼で追加しました。エディターの「サンプル2（隠し通路）」ボタンで作れます（48m に切り替わります）。

**内容**
- 48m × 48m、バイオームは遺跡。
- 高さ約 8m の岩の尾根が部屋を南北に分けています。
- 北側の聖域（宝箱、下り階段 `B2_hidden`、石柱、石像）へは、尾根を貫く**隠し通路だけ**が道です。
- 通路の入口：茂みで隠し、手がかりとして近くに石碑を置いています。
- 南側：開始地点、出入口 2、敵の候補 3、魔法陣。
- 確認結果（`tests/sample2_secret.js`）：
  - エラー 0・警告 0。
  - 通路内の点は、地形の高さ 8.09m の下を床の高さ 3.0m で通れる。
  - 通路を消すと、宝箱と下り階段に「歩いて行けません」が出る（＝通路が唯一の道）。

**隠し通路を実際に使うようになったので、Unity 向けの出力を追加しました**（Revision 1 の指摘「入口・出口・幅・天井高さ・経路・穴マスク」への対応です）
- `holes.png`：地形の穴。大きさは (頂点数 − 1)² セルで、0 = 穴、255 = 地表を残す。
  - 通路のうち岩の下を通るセル（地形が床より 0.3m 以上高いセル）だけを穴にします。
  - サンプル2では 80 セル（Unity x 16〜19、z 13.5〜20.5）で、経路と一致しています。
  - `meta.terrain.holes` と `holeCells` にも記載。
- `meta.secretPassages.passages[]`：
  - `id`：通路の最初のセルから決めます。通路の形を変えない限り同じです。
  - `cells`、`area_m2`
  - `entrances`：入口・出口の位置と床の高さ。
  - `route`：入口から出口までの床の上の経路で、約 1m 間隔。
  - `width`：幅の目安。
  - `rockAboveMax`：床の上にある岩の最大の厚さ。
- `clearanceHeight`：洞窟メッシュの天井の高さの目安（身長 + 0.6m = 2.4m）。
- Unity 側の作業（予定）：holes.png の穴を開け、route に沿って床・壁・天井の洞窟メッシュを置く。この作業と見た目は未確認です。
- 検証に追加したもの：通路の出入口が 2 か所未満なら警告、出入口に歩いて行けなければ警告。
